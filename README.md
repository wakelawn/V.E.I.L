# VEIL — Versatile Execution & Intelligence Layer

VEIL is a **SQL Query Analyzer and Optimization Engine**.  
It takes a SQL query, breaks it into tokens, parses its structure into an AST, and uses PostgreSQL execution-plan information to analyze the query.

# Overview

VEIL processes SQL queries through a structured pipeline:

```text
SQL Query
   ↓
Lexer
   ↓
Tokens
   ↓
Parser
   ↓
AST
   ↓
Analysis
   ↓
PostgreSQL EXPLAIN
   ↓
Plan Summary
   ↓
Optimization Recommendations
```

The current implementation focuses on:

- lexical analysis
- syntactic analysis
- AST construction
- PostgreSQL execution-plan retrieval
- simplified execution-plan summary

Future work may include:

- semantic analysis
- deeper plan-tree analysis
- full optimizer
- intelligent index recommendation engine

# Core SQL Engine Components

## 1. Lexer

### What does it do?

The **Lexer** takes raw SQL text and breaks it into small units called **tokens**.

### Example

Input SQL:

```sql
SELECT name FROM projects WHERE id = 1;
```

Tokenized output:

```text
SELECT
IDENTIFIER(name)
FROM
IDENTIFIER(projects)
WHERE
IDENTIFIER(id)
EQUALS(=)
NUMBER(1)
SEMICOLON
EOF
```

### Explanation

> The lexer performs lexical analysis. It converts the SQL string into a sequence of meaningful tokens.

---

## 2. Token / TokenType

### TokenType

`TokenType` defines what kind of token something is.

Examples:

| TokenType   | Meaning                         |
|-------------|---------------------------------|
| `SELECT`    | SQL SELECT keyword              |
| `FROM`      | SQL FROM keyword                |
| `WHERE`     | SQL WHERE keyword               |
| `IDENTIFIER`| Table, column, or object name   |
| `NUMBER`    | Numeric literal                 |
| `STRING`    | String literal                  |
| `EQUALS`    | Equality operator               |
| `COMMA`     | Comma separator                 |
| `STAR`      | `*` symbol                      |
| `SEMICOLON` | Statement terminator            |
| `EOF`       | End of input                    |

### Token

A `Token` stores:

- `type`
- `value`

Example:

```text
IDENTIFIER(name)
```

Meaning:

| Field | Value      |
|-------|------------|
| Type  | IDENTIFIER |
| Value | name       |

### Explanation

> TokenType defines the categories of SQL elements, while Token stores the category and actual value.

---

## 3. Parser

### What does it do?

The **Parser** takes the tokens generated by the lexer and checks whether they follow VEIL's SQL grammar.

### Example Grammar Flow

```text
SELECT → columns → FROM → table → WHERE → condition
```

After validation, the parser builds the **AST**.

### Explanation

> The parser performs syntactic analysis. It verifies the token sequence according to the grammar and constructs the abstract syntax tree.

---

## 4. ParseException

`ParseException` is used when the query does not follow the supported grammar.

### Example Error

```text
Expected SELECT but found IDENTIFIER
```

### Explanation

> ParseException reports syntax errors when the token sequence doesn't match the supported grammar.

---

## 5. AST

### What is an AST?

AST stands for **Abstract Syntax Tree**.

The AST represents the structure of the SQL query as Java objects.

### Example

For the query:

```sql
SELECT name FROM projects WHERE id = 1;
```

The AST can be visualized as:

```text
SelectStatement
├── Columns
│   └── name
├── Table
│   └── projects
└── WhereCondition
    ├── column = id
    ├── operator = =
    └── value = 1
```

### Explanation

> The AST is the structured internal representation of the SQL query. It allows later components to analyze and optimize the query without working directly with the original string.

---

## 6. SelectStatement

`SelectStatement` represents the complete SELECT query.

It currently contains:

- `columns`
- `table`
- `whereCondition`

### Explanation

> SelectStatement is the AST node representing a SELECT statement.

---

## 7. TableReference

`TableReference` represents the table being queried.

### Example

```sql
projects
```

### Explanation

> TableReference represents the table used by the SQL statement.

---

## 8. WhereCondition

`WhereCondition` represents the filtering clause of the query.

### Example

```sql
WHERE id = 1
```

It stores:

| Field    | Value |
|----------|-------|
| column   | id    |
| operator | =     |
| value    | 1     |

### Explanation

> WhereCondition represents a filtering condition in the query.

# Application / Backend Layer

## 9. Spring Boot

Spring Boot is **not** the SQL engine itself.

It provides the application/backend layer and exposes APIs such as:

| Endpoint          | Purpose                                  |
|-------------------|------------------------------------------|
| `/api/analyze`    | Analyze a SQL query                      |
| `/api/database`   | Retrieve PostgreSQL metadata             |
| `/api/explain`    | Retrieve execution plan for a SQL query  |

### Explanation

> Spring Boot provides the REST API and application infrastructure around the VEIL SQL engine.

## 14. ExplainService

`ExplainService` is one of the most important new parts of VEIL.

It sends:

```sql
EXPLAIN (FORMAT JSON)
```

to PostgreSQL.

### Example

Original query:

```sql
SELECT * FROM projects WHERE id = 1;
```

Internally becomes:

```sql
EXPLAIN (FORMAT JSON)
SELECT * FROM projects WHERE id = 1;
```

PostgreSQL returns information such as:

| Field          | Meaning                          |
|----------------|----------------------------------|
| Node Type      | Operation used by PostgreSQL     |
| Startup Cost   | Estimated startup cost           |
| Total Cost     | Estimated total cost             |
| Plan Rows      | Estimated number of rows         |
| Relation Name  | Table or relation being accessed |
| Index Name     | Index used, if any               |

### Explanation

> ExplainService obtains the PostgreSQL execution plan in JSON format so VEIL can analyze query execution behavior.

---

## 15. ExplainController

### Endpoint

POST /api/explain
```

### Example Input

```

### Explanation

> ExplainController provides an API endpoint for obtaining the execution plan of a read-only query.

---

## 16. PlanSummary

Instead of showing a huge raw PostgreSQL JSON response, VEIL extracts the important fields into a simpler model.

### PlanSummary Fields

| Field           | Meaning                          |
|-----------------|----------------------------------|
| `nodeType`      | Type of execution operation      |
| `relation`      | Table or relation being accessed |
| `index`         | Index used, if any               |
| `startupCost`   | Estimated startup cost           |
| `totalCost`     | Estimated total cost             |
| `estimatedRows` | Estimated number of rows         |

### Example

| Field         | Value          |
|---------------|----------------|
| Node Type     | Index Scan     |
| Relation      | projects       |
| Index         | projects_pkey  |
| Startup Cost  | 0.15           |
| Total Cost    | 8.17           |
| Rows          | 1              |

### Explanation

> PlanSummary converts the raw PostgreSQL execution-plan information into a simpler structure that VEIL can present and analyze.

# Database Structure

The PostgreSQL database used by VEIL is:

```text
veil
```

It currently has **5 main tables**.

---

## 17. projects

### Purpose

Stores the projects/workspaces in VEIL.

### Example

| Field       | Value                          |
|-------------|--------------------------------|
| id          | 1                              |
| name        | VEIL Demo                      |
| description | SQL Query Analyzer...          |

### Relationship

```text
1 project → many queries
```

### Explanation

> The projects table stores the logical projects under which SQL queries are organized.

---

## 18. queries

### Purpose

Stores the SQL queries submitted to VEIL.

### Important Fields

| Field             | Meaning                              |
|-------------------|--------------------------------------|
| id                | Primary key                          |
| project_id        | Foreign key to projects              |
| query_text        | Original SQL query                   |
| normalized_query  | Normalized version of the SQL query  |
| status            | Current status of the query          |
| created_at        | Timestamp when query was created     |

### Example

| Field        | Value                                            |
|--------------|--------------------------------------------------|
| project_id   | 1                                                |
| query_text   | SELECT name FROM projects WHERE id = 1;          |

### Explanation

> The queries table stores the SQL submitted for analysis and links each query to a project.

---

## 19. query_analysis

### Purpose

Stores the analysis result of a query.

It can contain:

- `token_count`
- `ast_text`
- `complexity`
- `estimated_cost`

### Relationship

```text
1 query → 1 analysis
```

This is enforced because `query_id` is `UNIQUE`.

### Explanation

> The query_analysis table stores the results produced when VEIL analyzes a query.

---

## 20. optimization_suggestions

### Purpose

Stores recommendations generated by VEIL.

Example suggestion types:

| Type        | Meaning                                  |
|-------------|------------------------------------------|
| INDEX       | Suggests index-related improvements      |
| PROJECTION  | Suggests selecting fewer/better columns  |
| FILTER      | Suggests filtering improvements          |
| JOIN        | Suggests join-related improvements       |

### Example Suggestions

```text
Avoid SELECT *
Consider an index on id
```

### Relationship

```text
1 query → many suggestions
```

### Explanation

> The optimization_suggestions table stores recommendations that VEIL generates for improving queries.

---

## 21. query_executions

### Purpose

Stores information about query execution.

### Important Fields

| Field              | Meaning                              |
|--------------------|--------------------------------------|
| execution_time_ms  | Time taken to execute the query      |
| rows_returned      | Number of rows returned              |
| actual_cost        | Actual or observed cost information  |
| executed_at        | Timestamp when execution occurred    |

### Relationship

```text
1 query → many executions
```

This will become more important when VEIL starts using:

```sql
EXPLAIN ANALYZE
```

### Explanation

> The query_executions table stores execution measurements so VEIL can later compare query performance.

# Indexes

VEIL uses both **automatic indexes** and **explicit indexes**.

---

## Automatic Indexes

Primary keys automatically get indexes.

Therefore, the following indexes exist automatically:

| Index Name                         | Created By                  |
|------------------------------------|-----------------------------|
| `projects_pkey`                    | Primary key on `projects`   |
| `queries_pkey`                     | Primary key on `queries`    |
| `query_analysis_pkey`              | Primary key on `query_analysis` |
| `optimization_suggestions_pkey`    | Primary key on `optimization_suggestions` |
| `query_executions_pkey`            | Primary key on `query_executions` |

Also:

```sql
query_analysis.query_id UNIQUE
```

creates a unique index.

---

## Explicit Indexes

## 22. idx_queries_project_created

### Definition

```sql
CREATE INDEX idx_queries_project_created
ON queries(project_id, created_at DESC);
```

### Purpose

Efficiently retrieve queries for a project, newest first.

### Example Query

```sql
SELECT *
FROM queries
WHERE project_id = 1
ORDER BY created_at DESC;
```

### Explanation

> This composite index supports filtering queries by project and retrieving them in descending creation order.

---

## 23. idx_suggestions_query

### Definition

```sql
CREATE INDEX idx_suggestions_query
ON optimization_suggestions(query_id);
```

### Purpose

Quickly find suggestions belonging to a query.

### Example Query

```sql
SELECT *
FROM optimization_suggestions
WHERE query_id = 1;
```

### Explanation

> This index speeds up retrieval of optimization suggestions for a specific query.

---

## 24. idx_executions_query_time

### Definition

```sql
CREATE INDEX idx_executions_query_time
ON query_executions(query_id, executed_at DESC);
```

### Purpose

Retrieve execution history for a query, newest first.

### Example Query

```sql
SELECT *
FROM query_executions
WHERE query_id = 1
ORDER BY executed_at DESC;
```

### Explanation

> This composite index supports retrieving a query's execution history ordered from newest to oldest.

---

## 25. Most Important Index Question

### Question

Why don't you index every column?

### Answer

> Indexes improve read performance for supported access patterns, but they consume storage and add overhead to inserts, updates, and deletes. Therefore, indexes should be designed based on actual query patterns.

---

## 26. Most Important PostgreSQL Question

### Question

Does a foreign key automatically create an index?

### Answer

No. PostgreSQL does **not** automatically create an index on the referencing side of a foreign key.

That is why explicit indexes were created where the application is expected to frequently query by foreign key.

---

# 27. What is EXPLAIN?

### Answer

> EXPLAIN shows the execution plan chosen by PostgreSQL for a query, including operations such as scans, joins, estimated costs, and estimated rows.

VEIL currently uses:

```sql
EXPLAIN (FORMAT JSON)
```
